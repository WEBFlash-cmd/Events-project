# Участники и продажи мероприятия

Оба endpoint требуют `Authorization: Bearer <токен Sanctum>` и разрешение
`events.reports` у владельца мероприятия либо `events.reports-any` (администратор).
Чужой организатор и участник получают 403, гость — 401, отсутствующий или
нечисловой ID мероприятия — 404. Владелец без разрешения тоже получает 403.
Отчёты доступны для всех статусов мероприятия, включая черновики и отменённые.

## Список участников

`GET /api/events/{event}/participants?page=1&per_page=15&status=active`

Пагинация: по умолчанию 15, максимум 100 записей; `page` — целое от 1.
Необязательный `status`: `active`, `used`, `cancelled`. Неверные значения — 422.
Передача непустых `user_id` и `event_id` запрещена: мероприятие определяется маршрутом.
Сортировка по `created_at DESC, id DESC`. Пустая страница — 200 с пустым `data`.

Одна запись — один выданный билет оплаченного заказа данного мероприятия:

- `id`, `number`, `order_id`, `status`, `refund_required`, `checked_in_at`, `created_at`;
- `user: {id, email}` — владелец билета;
- `ticket_type: {id, name}` — тип билета.

У покупателя с двумя билетами две записи. Имена отдельных посетителей пока не
хранятся: владелец билета — покупатель. Отменённые билеты остаются в истории;
чтобы увидеть только действующие, используйте `status=active`.
Неоплаченные заказы без выданных билетов в список не попадают.
Пароли, токены, роли и платёжные ссылки в ответ не включаются.

## Сводка продаж

`GET /api/events/{event}/sales`

Ответ в `data`:

| Поле | Значение |
|---|---|
| `event_id`, `event_status` | Мероприятие и текущий статус |
| `orders` | Число заказов отдельно по pending, paid, cancelled, expired |
| `tickets.sold` | Все выданные билеты paid-заказов, включая used и cancelled |
| `tickets.active` | Из них с текущим статусом active |
| `tickets.checked_in` | Из них с сохранённым временем прохода |
| `tickets.refund_required` | Из них с отметкой необходимости возврата |
| `tickets.available` | Текущая сумма quantity типов билетов |
| `buyers` | Уникальные владельцы выданных билетов paid-заказов |
| `money.currency` | UZS |
| `money.gross_received` | Сумма подтверждённых платежей paid/refund_required |
| `money.refund_required` | Из этой суммы платежи с флагом refund_required |
| `money.excluding_required_refunds` | gross_received минус refund_required |
| `ticket_types` | Типы билетов: id, name, текущая price, available, sold, active, checked_in, refund_required |

Деньги возвращаются строками с двумя знаками после точки, например `"100000.00"`.
Расчёты используют целые тийины без float. Текущая цена типа билета не используется
для пересчёта прошлых продаж. Платёж считается один раз независимо от числа билетов.
Неоплаченные брони не считаются выданными билетами или доходом; их количество
уже исключено из текущего доступного остатка до отмены/истечения брони.

Поздняя успешная оплата отменённого/истёкшего заказа тоже входит в полученные
средства и сумму для возврата, хотя билетов по ней не выпущено.
`excluding_required_refunds` — расчётная сумма после исключения обязательств
по возвратам; она не означает, что деньги уже фактически возвращены.
После отмены сохраняются число проданных билетов и история check-in,
а флаги возврата отражаются отдельно. Категории билетов могут пересекаться:
использованный билет после отмены одновременно checked_in и refund_required.
Доступный остаток отменённого мероприятия не означает, что продажи открыты.

На время построения сводки используется общая блокировка строки мероприятия.
Она согласована с транзакциями покупки, check-in и отмены, чтобы части сводки
не относились к разным состояниям продажи. Построение сводки может кратко
задержать запись по этому мероприятию.

## Проверка

1. С токеном организатора вызвать оба endpoint для своего мероприятия.
2. Купить два билета и отметить проход одного: sold увеличится на 2,
   checked_in — на 1, а платёж попадёт в сумму один раз.
3. Токеном другого организатора повторить запрос — ожидается 403.
4. После отмены проверить флаги возврата и сохранённую историю.

Код: `EventReportController`, `EventReportService`, `IndexEventParticipantsRequest`,
`EventPolicy::viewReports`. Права добавляет миграция
`2026_10_20_140000_add_event_report_permissions.php`.
