# Заказы и резерв билетов

## Создание

`POST /api/events/{event}/orders`, авторизация Sanctum.

```json
{"items":[{"ticket_type_id":1,"quantity":2}]}
```

Сервер берёт цены из БД, уменьшает доступный остаток и сохраняет заказ
со статусом `pending`. Срок резерва возвращается в `data.expires_at` (UTC).
По умолчанию он составляет 15 минут, но не может быть позже начала мероприятия.
Настройка: `ORDER_RESERVATION_MINUTES` в `.env` (целое число минут, минимум 1).
После изменения настройки при включённом кеше конфигурации его нужно пересобрать.

## Отмена

`POST /api/orders/{order}/cancel`, без тела запроса, авторизация Sanctum.

Отменить неоплаченный заказ может владелец или пользователь с RBAC-разрешением
`orders.cancel-any` (назначается администратору миграцией).
Успех: `200` и заказ в `data`; чужой заказ: `403`; оплаченный заказ: `409`.

Отмена переводит `pending` в `cancelled` и возвращает билеты в доступный остаток.
Если срок уже истёк, статус становится `expired`.
Повторная отмена `cancelled`/`expired` возвращает текущее состояние без повторного
увеличения остатка. Заказ и его позиции сохраняются.

## Автоматическое истечение

Команда `php artisan orders:expire` обрабатывает просроченные `pending`-заказы.
Laravel Scheduler запускает её каждую минуту. Фактическое освобождение резерва
может произойти примерно на минуту позже `expires_at`.

В Docker Compose добавлен сервис `scheduler`, который выполняет `schedule:work`.
Из папки проекта после миграций:

```powershell
docker exec events-project-php-1 php artisan migrate
docker compose --project-directory docker up -d --no-build scheduler
```

Разовый запуск и проверка расписания:

```powershell
docker exec events-project-php-1 php artisan orders:expire
docker exec events-project-php-1 php artisan schedule:list
```

Изменения статуса и остатка выполняются в одной транзакции. Порядок блокировок:
мероприятие → заказ → типы билетов. Статус повторно читается под блокировкой,
поэтому повторный запуск не возвращает резерв дважды и не затрагивает `paid`.
При изменении количества типов билетов вместимость учитывает доступные,
зарезервированные и проданные места.

Новая миграция назначает старым `pending`-заказам срок от их `created_at`.
У старых просроченных заказов резерв будет освобождён при первом запуске команды.

## Оплата через Training Payment System

Настройки в локальном `application/.env` (секрет не коммитить):

```dotenv
TRAINING_PS_URL=http://host.docker.internal:8092
TRAINING_PS_CASHBOX_ID=1
TRAINING_PS_SECRET=<секрет кассы>
TRAINING_PS_TIMEOUT=20
```

Создание заказа теперь сохраняет запись `payments`, затем обращается к
`POST /api/create-payment` платёжной системы вне транзакции резервирования.
`amount` — целое число тийинов: `100000.00` сум = `10000000` тийинов.
Платежи с нулевой суммой не поддерживаются этим API и отклоняются с `422` без резерва.

Ответ создания заказа остаётся `201`; в `data.payment` возвращаются:

- `reference` — уникальный UUID операции; именно он передаётся внешней системе как `order_id`;
- `payment_url` — полученная ссылка на оплату;
- `status` — состояние платежа;
- `error_code` — общий код ошибки обращения к шлюзу, если она произошла.

`201` подтверждает создание заказа, а не успешное получение ссылки. Если шлюз
недоступен или его ответ неоднозначен, заказ и резерв сохраняются до обычного
истечения срока, а платёж получает `unknown` и `payment_url: null`.
При явном отказе шлюза состояние — `creation_failed`. Автоматический повтор
создания отключён: API провайдера не возвращает старую ссылку по `order_id`,
а сетевой таймаут не доказывает, что платёж не был создан.
В такой ситуации нужна сверка с платёжной системой. Не создавайте повторные
заказы вслепую; существующий можно отменить обычным endpoint отмены.

### Webhook

В кассе должны быть настроены адреса:

| Поле | Для локального запуска |
|---|---|
| Webhook URL | `http://host.docker.internal:8093/api/payments/webhook` |
| Success URL | `http://localhost:8092/?result=success` (временный возврат на учебный интерфейс) |
| Fail URL | `http://localhost:8092/?result=fail` (временный возврат на учебный интерфейс) |

Уведомление `POST /api/payments/webhook` содержит `order_id` (UUID операции),
`amount` (тийины), `status` (`1` — оплачено, `2` — неуспех).
В `X-Signature` передаётся HMAC-SHA256. Поля сортируются по ключу,
подпись вычисляется от строки `key|value|key|value` секретом кассы.
Неверная подпись — `403`; неверная сумма/касса/статус — `422`;
неизвестная операция — `404`; конфликт терминальных статусов — `409`.

Успешная оплата действующего резерва атомарно переводит заказ и платёж в `paid`
и создаёт по одному билету на каждую единицу позиции. У билетов уникальные UUID,
а пара `(order_item_id, sequence)` дополнительно защищена уникальным индексом.
`OrderPaid` отправляется после фиксации транзакции.

Повторный одинаковый webhook возвращает `200` без дублирования билетов.
Неуспешная оплата отменяет `pending`-заказ и возвращает резерв один раз.
Успешная оплата после отмены, истечения или закрытия мероприятия сохраняется
как `payment.status = refund_required` и `payment.refund_required = true`.
Заказ остаётся закрытым; билеты не выпускаются, остаток повторно не уменьшается.
Фактический возврат денег выполняется отдельно и здесь не реализован.

### Просмотр результата

`GET /api/orders/{order}` возвращает заказ с `items`, `payment`, `tickets`.
Доступ: Sanctum + владелец либо RBAC-разрешение `orders.view-any` (администратор).
Редирект браузера с платёжной страницы не подтверждает оплату: источник истины
только подписанный webhook. Для ручной проверки откройте
`data.payment.payment_url`, выберите `Success` или `Failure`, затем запросите заказ.

В тестах внешние запросы запрещены по умолчанию и подменяются ответами шлюза;
реальная локальная касса при запуске `artisan test` не используется.

## Списки своих заказов и билетов

Все три endpoint требуют `Authorization: Bearer <токен Sanctum>`:

| Endpoint | Результат |
|---|---|
| `GET /api/orders` | Только заказы текущего пользователя, включая неоплаченные и отменённые |
| `GET /api/tickets` | Только выпущенные билеты текущего пользователя |
| `GET /api/tickets/{ticket}` | Подробности билета по его числовому ID |

Списки отсортированы по `created_at DESC, id DESC`: сначала новые записи,
при совпадении времени — сначала запись с большим ID. По умолчанию возвращается
15 записей. Параметры `page` и `per_page` — положительные целые, `per_page` не более 100.
Например: `GET /api/tickets?page=2&per_page=10`.

В ответе списков верхний уровень содержит `data` (массив записей), `current_page`,
`per_page`, `total`, `last_page`, `next_page_url` и другие поля стандартной
пагинации Laravel. Пустой список и страница за пределами списка возвращают `200`
с пустым `data`. Неверные параметры и попытка передать непустой `user_id` дают `422`.
Счётчик `total` учитывает только собственные записи.

Заказ в списке включает мероприятие с местом проведения, позиции и платёж.
Билет включает мероприятие с местом, тип билета и краткий заказ (`id`, `status`).
Исторические билеты остаются доступны владельцу, даже если мероприятие отменено.
Номера билетов и состав заказов другого покупателя в списки не попадают.

Просмотр одного билета разрешён владельцу либо пользователю с разрешением
`tickets.view-any` (администратор). Чужой билет — `403`, отсутствующий — `404`,
запрос без авторизации — `401`. Организатор мероприятия не получает через этот
endpoint доступ к билетам других покупателей; проверка на входе будет отдельной
операцией. Персональные списки администратора также показывают только его записи;
это не административные списки всех покупок.

## Check-in билета

```http
POST /api/events/{event}/tickets/{ticket}/check-in
Authorization: Bearer <токен организатора или администратора>
```

`event` и `ticket` — числовые ID. Тело запроса не требуется: статус, время и
сотрудник определяются сервером. Попытка передать непустые `status`, `checked_in_at`
или `checked_in_by` возвращает `422`.

Организатор должен владеть мероприятием и иметь разрешение `tickets.check-in`.
Разрешение `tickets.check-in-any` позволяет администратору отмечать проход
на любое мероприятие. Сам покупатель не может зарегистрировать свой проход.

Check-in разрешён на опубликованное мероприятие до его `ends_at`, включая
время до начала (ранний вход). Нижняя граница времени входа пока не задана.
Отменённые, завершённые мероприятия и черновики не принимают билеты.

Проверяются принадлежность билета мероприятию, оплаченный заказ того же
владельца и мероприятия, статус билета `active` и отсутствие `checked_in_at`.
Проверки выполняются внутри транзакции после блокировки и повторного чтения
мероприятия, заказа и билета. Права на актуальное мероприятие также проверяются
повторно. При двух параллельных запросах один обновляет билет, а другой после
ожидания блокировки видит `used` и получает отказ.

Успех — `200` с билетом в `data`:

- `status: used`;
- `checked_in_at` — время прохода (дата и время UTC);
- `checked_in_by` — ID сотрудника.

Повторный проход, неоплаченный заказ, неактивный билет и закрытое мероприятие
возвращают `409`. Запрос не изменяет первоначальные время и сотрудника.
Без авторизации — `401`, без права check-in — `403`, отсутствующий билет или
билет другого мероприятия — `404` (в том числе для администратора).
Списки и просмотр своих билетов также возвращают сохранённые поля check-in.

## Письмо после оплаты

`SendPurchaseConfirmation` слушает `OrderPaid` и выполняется через очередь
`notifications` после фиксации транзакции. Письмо отправляется на email владельца
заказа и содержит название мероприятия, дату с часовым поясом, место,
оплаченную сумму и номера всех выпущенных билетов.

Обработчик повторно проверяет статус заказа и блокирует его строку.
После успешной отправки записывает `purchase_confirmation_sent_at`.
Повторный webhook не создаёт новое событие, а повторная задача для уже
обработанного заказа не отправляет письмо. Для `pending`, `cancelled`, `expired`
и платежей с `refund_required` подтверждение покупки не отправляется.

При ошибке почтового транспорта задача повторяется до трёх попыток с задержками
10 и 60 секунд. Ошибка не отменяет оплаченную покупку и выпущенные билеты;
отметка отправки остаётся пустой до успешной доставки в почтовый транспорт.
SMTP и база не образуют общую транзакцию: при аварийном завершении строго между
приёмом письма SMTP-сервером и сохранением отметки возможен повтор при ретрае.

В Docker Compose добавлен сервис `queue`:

```powershell
docker exec events-project-php-1 php artisan migrate
docker compose --project-directory docker up -d --no-build queue
docker compose --project-directory docker logs --tail 20 queue
```

Для локальной проверки в `application/.env`:

```dotenv
QUEUE_CONNECTION=database
MAIL_MAILER=smtp
MAIL_HOST=mailhog
MAIL_PORT=1025
```

После изменения конфигурации очистите её кеш и перезапустите worker.
Письма Events-project доступны на `http://localhost:8025` (почта training-ps
использует другой адрес — `http://localhost:8026`).
Создайте новый заказ и оплатите его через `Success`; подтверждение появится
после обработки очереди. Исторические оплаченные заказы автоматически не
рассылаются. Повторная отправка `OrderPaid` для старого оплаченного заказа
позволяет проверить обработчик; повторения безопасны после сохранения отметки.

Проверка задач, исчерпавших попытки:

```powershell
docker exec events-project-php-1 php artisan queue:failed
```

После устранения причины можно повторить конкретную задачу командой
`php artisan queue:retry <uuid>` внутри PHP-контейнера.
